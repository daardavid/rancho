## Problem

What real ranch or product problem are we trying to improve?

## User / Actor

Who experiences it, or who benefits?

## Why this matters

Explain the relationship to the items that apply:

- profitability
- cost
- risk
- operational effort
- decision quality
- control or visibility
- reliable reusable data

## Hypothesis

What do we currently believe this increment will improve?

Keep the hypothesis separate from a known fact.

## What we want to learn

What uncertainty should real implementation or use reduce?

This section matters especially for an MVP or pilot increment.

## User outcome

What should the user be able to accomplish when this increment works?

Use ranch language.

## UX flow

Describe the conceptual workflow.

Do not prescribe technical implementation unless the workflow requires it.

## Domain facts involved

List the authoritative facts or business concepts this increment affects.

Reference existing sources. Do not invent missing business meaning.

## Data produced / improved

What trustworthy, reusable information becomes available?

Include only data with a plausible use.

## Decision enabled

What decision or control becomes easier or better?

If none is known, write `UNKNOWN` and reconsider the value proposition.

## Future evolution value

What reasonable future capability, if any, does this preserve or enable?

Do not use this section to prebuild speculative technology.

`None required` is a valid answer.

## Unknowns

### Blocking

Unknowns that must be resolved before `READY`.

### Non-blocking

Unknowns preserved explicitly.

## In scope

The exact product scope.

## Explicitly out of scope

Important nearby work this increment will not implement.

## Relevant Product Decisions

PD ids, when they exist.

## Relevant domain sources

Repository links or ids.

## Relevant ADRs

Only architecture decisions this increment actually touches.

## Relevant UX Principles

Only principles that materially apply.

## Acceptance criteria

Use observable outcomes.

Do not write criteria that only list implementation tasks.

## Validation plan

How will we know the increment works?

Use only the sources that apply:

- automated tests
- workflow review
- product or UX review
- pilot observation
- real ranch use

## Accepted UX debt

If meaningful temporary friction is accepted, record the debt, the reason, and the revisit trigger.

Otherwise: None.

## Risks / failure modes

Only meaningful ones.

## Follow-up / revisit triggers

What future evidence should cause a reassessment?

## PR mapping

Leave empty until execution planning.

An increment may map to one PR or to several.

## Learning after validation

Leave empty before validation.

After use, record:

- what happened
- which assumptions were confirmed or refuted
- UX findings
- domain findings
- new opportunities or questions
- the effect on the next priority
